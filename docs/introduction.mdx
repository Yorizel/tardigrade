Tardigrade is a TypeScript framework for durable agents built on Alchemy Domain and Effect. Domain aggregates own business decisions, events and state; native Effect Workflows, Activities and Cluster run durable work. The current native implementation includes Domain APIs, a Cluster agent runner and an interpreter adapter. The target architecture applies Elm ideas to explicit messages and commands without introducing a second owner for domain state. See [Architecture](/docs/architecture) for the boundary and testing direction.

## Run Tardigrade

Create the non-AI Counter example:

```sh
tdg init counter --template quickstart
cd counter
cp .env.example .env
```

Set `TARDIGRADE_TOKEN` and `TARDIGRADE_SUBJECT` in `.env`. The generated `actor.ts` contains the Counter aggregate, Increment and Decrement commands, owner checks, events and native replies. A policy starts a native Effect workflow when the resulting count is positive and even. Its Activity invokes the configured notification external system. No model provider or model lock is involved.

Run `bun run dev` for Alchemy Cloudflare. For an ephemeral Bun development server, run `bun run dev:memory`; both its counter state and workflow checkpoints end with the process. `PORT` controls the Bun server port and `TARDIGRADE_URL` selects the endpoint used by the client.

Use the generated native CLI in another terminal:

```sh
bun run cli increment --json '{"target":"main","input":{},"commandId":"first"}'
bun run cli increment --json '{"target":"main","input":{},"commandId":"second"}'
bun run cli decrement --json '{"target":"main","input":{},"commandId":"third"}'
bun run cli counter get --key main
```

The command replies contain counts 1, 2 and 1. Retry the same command ID to receive its original receipt. A different caller cannot read or mutate the counter or replay its receipt. Each counter ID starts at zero before its first accepted command. Counts use the safe integer range of native JavaScript numbers; incrementing or decrementing past that range is rejected.

Notifications use the counter ID and committed event version as their workflow identity. Replaying a completed workflow reuses its Activity checkpoint. External delivery remains at least once: a crash after an external effect and before its checkpoint can repeat the effect. Applications whose external notification matters provide an idempotent adapter using that identity.

## Cloud

`worker.ts` hosts CounterApi through native Domain Durable Objects. `alchemy.run.ts` owns its Alchemy stack and storage declarations. `notifyLayer` supplies the notification implementation, and the native Effect workflow engine supplied by the Cloudflare platform owns its checkpoints.

```sh
bun run plan:cloudflare --stage prod
bun run deploy:cloudflare --stage prod
```

Keep the stack's `.alchemy` state between deployments. Local HTTP fixtures and typechecks do not prove a deployment or cloud recovery.

## AI agents

`tdg init assistant` generates the native Domain and Cluster agent stack. Configure its native provider Layer and required settings, then run the state server and runner as described in the [Alchemy guide](/docs/platforms/alchemy).
